# Prompt 与调用参数

这份记录里的 Prompt 都是中文口语，没有做“提示词工程”的花活。核心是：**小步走、先看状态、失败就换目标、把计划写在游戏笔记里，而不是塞进一次上下文。**

---

## 1. 游戏回路：每轮的主 Prompt

```text
你是《星露谷物语》里的真人玩家，用 stardew MCP 自己玩，不要问玩家问题。
当前现场：{facts 或 “刚进存档”}

每轮的工作方式：
1. 先调用一次 get_state。里面有你上次写的长期笔记、背包、文字地图和出口。
2. 这一轮只推进一小步：做最多 3 个写操作（开垦/播种/浇水/收获/走路/买东西都算），
   例如 move_to(x,y)、travel_to(location)、till_area、plant_seeds、water_crops、
   harvest_crops、clear_area、fish、explore_mine、buy、sell、give_gift、sleep；
   拿不准就用 get_guide 查攻略。
3. 用文字地图确认目标格能站人再 move_to，不要猜坐标；目标不可站立时换旁边一格。
   同一个动作失败一次就换目标，不要反复重试。
4. 如果 get_state 显示还开着界面：商店/背包用 close_menu，对话框用 dialogue 继续或关闭，
   处理完再继续或收尾。
5. 体力低于 30 或时间到 23:30，就回农舍 sleep；背包满就 ship_items/store_items。
6. 做完先调用 update_notes 写下接下来 1-2 天的计划（例如「浇水、攒钱买种子、下矿」），
   最后用鱼的口吻对观众说一句自然的话（第一人称，40 字以内），
   说说这轮做了什么或接下来要干嘛；不要写列表、标题或「这轮做了：」开头；
   不要调用 shell、文件、代码工具。
```

### 每条规则为什么存在

| 规则 | 解决的问题 |
| --- | --- |
| 先 `get_state` | 上一轮的缓存会过期；Mod 的笔记、背包、地图都在里面 |
| 最多 3 个写操作 | 一次做太多，模型会规划到一半就超时，留下一地半成品 |
| 用文字地图确认可站立 | 直接猜坐标会撞墙、卡住、无限重试 |
| 失败一次就换目标 | LLM 很容易对同一个不可达目标重试到 turn 上限 |
| 先处理界面/对话 | 商店、背包、对话框会挡住后续动作，甚至冻结时间 |
| 低体力/23:30 睡觉 | 防止凌晨两点还在矿洞里；睡觉还能触发“新的一天”占位 |
| `update_notes` | 把 1–2 天计划写进游戏侧，下一轮还能读到；不依赖长上下文 |
| 最后一句 ≤40 字 | 这句话会直接进 TTS 和字幕，太长会拖节奏、也容易念得怪 |
| 禁止 shell/文件/代码工具 | 只给它 MCP 工具；不要让“玩游戏”变成“改电脑” |

### 好汇报 vs 坏汇报

**坏（像工作日志）：**

```text
这轮做了：从镇上出发，去山上湖钓了两轮，共钓到5条鲤鱼、2条鲢鱼、1条大嘴鲈鱼等，
回家把鱼放进出货箱（约+250g）；体力降到27后返回农场，用镰刀清了17处杂草，然后回家睡觉。
```

问题：太长、像报表、数字很多但观众记不住；读出来更灾难。

**好（像主播说话）：**

```text
鱼今天钓了一下午，鱼竿都快举不动了，明天得先去买点种子。
```

规则：第一人称、一句、40 字以内、说“做了什么/接下来干嘛”，不列清单。

### 调参

| 参数 | 本实验值 | 说明 |
| --- | --- | --- |
| 每轮写操作 | ≤3 | 超过就容易超时/半成品 |
| `max_turns` | 36 | 一次 qodercli 调用的硬上限 |
| `timeout` | 600 秒 | 超时不致命，会保留已完成的动作 |
| 轮间隔 | 45 秒 | 太短会堆回合，太长会显得发呆 |
| 模型 | `Fast` | 低成本、低延迟；复杂规划再换强模型 |
| `get_state` 超时 | 30 秒 | 游戏卡顿时不要拖死整个回合 |

## 2. 聊天回路：注入“游戏现场”的那一段

```text
【星露谷现场】{facts}。这是你此刻在游戏里的真实情况，不要编造没发生的事。
回复观众时正常聊天，不用每句都汇报农场；只有话题相关时才自然提一句进展，
同一件事不要反复说。体力和金钱的数字要照抄现场，不要看错、省略或改写成大概。
```

### 为什么不是“每句都提游戏”

早期版本要求每次回复都带一句农场进展，结果：

- 观众问“你是什么模型”，回答也要拐到“鱼在农场忙活”；
- 同一句 `鱼在SeedShop忙活。` 反复出现，观众直接指出来。

现在的规则是：**话题相关才提**，且同一个 fallback 句子只追加一次，直到现场变化。`mention_probability` 仍然可以是 100，但“注入现场”不等于“强行说农场”。

### 数字照抄

模型会把 18 看成 81、把 70 说成“快没体力”，或者把昨天的雨天说成今天。除了缩短 TTL，Prompt 里明确要求“照抄，不要改写”是最后一道防线。

## 3. qodercli 调用方式

本实验用的是 stream-json，方便逐个捕获 `tool_use` 做字幕和语音：

```text
qodercli -p \
  --input-format stream-json \
  --output-format stream-json \
  --max-turns 36 \
  --tools "" \
  --strict-mcp-config \
  --mcp-config '{"mcpServers":{"stardew":{"type":"http","url":"http://127.0.0.1:18080/mcp"}}}' \
  --allowed-mcp-server-names stardew \
  --allowed-tools "mcp__stardew__*" \
  -m Fast
```

stdin 写一行：

```json
{"type":"user","message":{"role":"user","content":"<上面的 prompt>"},"parent_tool_use_id":null}
```

然后逐行读 stdout：

- `type=assistant` 里的 `text` 是阶段性的汇报；`tool_use` 是动作，可用来推字幕/语音；
- `type=result` 是结束；遇到就停止读取，不要等进程自己退；
- 错误里如果包含 `maximum number of turns`，当成“做满上限”而不是致命错误；
- 不要继承宿主里的 `QODER*` 环境变量（除了登录 token），也不要带 `ELECTRON_RUN_AS_NODE`，否则 CLI 可能以为自己跑在宿主里。

> 认证信息只放在本机环境/登录态里，不要写进 prompt、仓库或日志。

## 4. 迁移到别的游戏

这套 Prompt 的结构可以复用，但要换掉三样东西：

1. **状态读取**：必须有一个稳定的 `get_state`，包含位置、资源、当前界面；
2. **动作集合**：高层动作（走过去、使用、购买、睡觉），不要暴露鼠标坐标和键盘宏；
3. **失败恢复**：每个动作要能返回“为什么失败”，模型才能换目标；否则它会无限重试。

如果游戏只有画面、没有文本状态，这套“盲操作”就不成立，需要视觉模型或屏幕 OCR，成本和延迟都会上一个台阶。

---

## 5. 不要做的事

- 不要让模型一次规划一整天；它会在第一个意外（下雨、NPC 挡路、背包满）之后全盘作废。
- 不要把完整背包、完整地图、完整日志塞进 Prompt；只给这一轮需要的摘要。
- 不要让模型自己决定“要不要用 shell 查一下”；工具白名单只留游戏 MCP。
- 不要在 Prompt 里写“必须成功”“不许失败”；它会更倾向于重复同一个失败动作。
- 不要用同一个模型同时做聊天和游戏还共享上下文；两边节奏和时效完全不同。
